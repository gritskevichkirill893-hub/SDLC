## 1. Введение {#1-introduction}

Пользователи — студенты, офисные сотрудники и фрилансеры — ведут списки дел в бумажных блокнотах, заметках телефона или универсальных приложениях-заметках. Такие инструменты не разделяют задачи по срочности и важности, не умеют напоминать о регулярных делах (оплата счетов, тренировки, еженедельные отчёты) и не позволяют разбить крупную задачу на подзадачи. В результате часть задач забывается или выполняется в последний момент.

### 1.1 Назначение документа {#11-document-purpose}

Настоящая спецификация требований к программному обеспечению (SRS) определяет функциональные и нефункциональные требования к настольному приложению **TaskFlow** (версия 0.1 / MVP). Документ описывает, **что** именно система должна делать и каким ограничениям и атрибутам качества она должна удовлетворять, не фиксируя низкоуровневых деталей реализации. Основная аудитория документа — разработчик, тестировщик (QA), заказчик (в рамках ролевой модели проекта) и преподаватель дисциплины «Жизненный цикл разработки программного обеспечения» (ЖЦРПО). Документ используется для проектирования архитектуры, реализации, приёмочного тестирования и верификации требований.

### 1.2 Область применения продукта {#12-product-scope}

**TaskFlow** (версия 0.1, первый релиз MVP) — это автономное (offline-first) настольное приложение-органайзер для персонального планирования личных и рабочих задач, не требующее регистрации и подключения к интернету. Продукт предназначен для быстрого создания задач (≤ 5 с), управления их приоритетами, дедлайнами и пользовательскими категориями, декомпозиции крупных дел на подзадачи с автоматическим расчётом прогресса, настройки повторяющихся задач и поддержания пользовательской мотивации за счёт показателя «серии» (streak) дней без пропущенных дедлайнов.

* **Входит в объём MVP (версия 0.1):** CRUD-операции над задачами, дедлайны с визуальным выделением истекающих (≤ 24 ч) и просроченных задач, 3 уровня приоритета, пользовательские категории с цветовой меткой, одноуровневые подзадачи с агрегированным прогрессом, повторяющиеся задачи с автосозданием следующего экземпляра, счётчик выполненных задач и «серия» (streak), фильтрация и сортировка, локальное хранение данных в SQLite.
* **Не входит в объём MVP (отложено на последующие релизы):** облачная синхронизация между устройствами, многопользовательские совместные списки, интеграция с внешними календарями (Google Calendar, Outlook), экспорт/импорт в CSV и ICS, отображение в виде календаря, системные push-уведомления ОС, веб- и мобильный клиенты.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

**TaskFlow** является самостоятельным, создаваемым с нуля (greenfield) однопользовательским настольным приложением, не входящим в состав сторонних корпоративных экосистем. В отличие от облачных решений (Todoist, Microsoft To Do, TickTick), приложение не взаимодействует с внешними веб-серверами, API облачной синхронизации или службами аутентификации. Все пользовательские данные хранятся локально на устройстве пользователя в файле базы данных SQLite, а взаимодействие с операционной системой ограничивается графической подсистемой Qt 6 и файловой системой ОС.

```text
+-------------------------------------------------------+
|              Пользователь (Desktop UI)                |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
|          Приложение TaskFlow (C++17 / Qt 6)           |
|  - Модуль управления задачами и подзадачами           |
|  - Движок повторяющихся задач (Recurrence Engine)     |
|  - Модуль фильтрации, сортировки и расчёта Streak     |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
|      Локальная БД SQLite (файловая система ОС)        |
+-------------------------------------------------------+
```

### 2.2 Функции продукта {#22-product-functions}

На верхнем уровне приложение **TaskFlow** предоставляет пользователю следующие возможности:
1. **Управление задачами:** создание, просмотр, редактирование, удаление задач и отметка их выполнения.
2. **Контроль сроков (дедлайнов):** задание даты и времени выполнения задачи с автоматическим визуальным выделением истекающих (≤ 24 ч) и просроченных задач.
3. **Приоритизация:** назначение каждой задаче одного из трёх уровней приоритета (Высокий, Средний, Низкий) с цветовой индикацией.
4. **Категоризация:** создание, переименование и удаление пользовательских категорий с индивидуальной цветовой меткой и фильтрацией по ним.
5. **Декомпозиция на подзадачи:** добавление произвольного количества подзадач первого уровня с индивидуальными отметками выполнения и автоматическим расчётом прогресса родительской задачи.
6. **Повторяющиеся задачи:** настройка периодичности (ежедневно, еженедельно по дням недели, ежемесячно по числу месяца, произвольный интервал в днях) и автоматическая генерация следующего экземпляра при завершении текущего.
7. **Мотивация и аналитика:** подсчёт выполненных задач за день и неделю, а также расчёт и отображение непрерывной «серии» (streak) дней без пропущенных дедлайнов.
8. **Поиск, фильтрация и сортировка:** быстрый отбор и упорядочивание списка задач по категории, приоритету, сроку выполнения и статусу.
9. **Автономное хранение данных:** надёжное сохранение всех данных в локальной БД SQLite без необходимости подключения к сети Интернет.

### 2.3 Ограничения продукта {#23-product-constraints}

* **CON-1 (Язык и стандарт разработки):** Ядро приложения и бизнес-логика должны быть реализованы на языке C++ стандарта не ниже C++17.
* **CON-2 (Графический фреймворк):** Пользовательский интерфейс должен быть разработан с использованием библиотеки Qt 6 (модуль Qt Widgets).
* **CON-3 (Хранилище данных):** Для хранения данных должна использоваться встраиваемая локальная реляционная СУБД SQLite без использования внешних серверов БД.
* **CON-4 (Автономность):** Приложение должно функционировать полностью локально (offline-first), не требовать регистрации/учётной записи и не выполнять сетевых запросов.
* **CON-5 (Целевые платформы):** Приложение должно собираться и функционировать на настольных операционных системах Windows 10/11 (x64) и Linux (Ubuntu 22.04+ x64).
* **CON-6 (Язык интерфейса):** Интерфейс пользователя и документация должны быть выполнены на русском языке.

### 2.4 Характеристики пользователей {#24-user-characteristics}

Целевая аудитория приложения представлена следующими основными классами пользователей:

| Класс пользователя | Характеристика и поведение | Уровень подготовки | Частота использования | Ключевые цели и потребности |
|---|---|---|---|---|
| **Студент** | Ведёт расписание лабораторных работ, курсовых проектов, экзаменов и личных дел; часто работает в условиях нестабильного интернета. | Базовый / продвинутый пользователь ПК | Ежедневно (несколько раз в день) | Разбиение крупных учебных работ на подзадачи, контроль дедлайнов сдачи, визуальная мотивация (streak). |
| **Офисный сотрудник / Фрилансер** | Управляет рабочими поручениями, регулярными отчётами, оплатой счетов и личными делами в едином окне. | Уверенный пользователь ПК | Ежедневно в течение рабочего дня | Разделение рабочих и личных задач по категориям, автоматизация повторяющихся задач, быстрый ввод. |
| **Разработчик / Преподаватель (при приёмке)** | Проверяет корректность работы бизнес-логики, граничные случаи повторений, локальное хранение и соответствие SRS. | Эксперт в области ИТ | Периодически (этапы тестирования и сдачи) | Прозрачность работы, предсказуемость поведения, отсутствие сбоев. |

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

* **Допущение 1:** Приложение используется одним человеком на одном персональном компьютере; одновременный доступ нескольких процессов к одному файлу базы данных SQLite не предполагается.
* **Допущение 2:** Системные часы и часовой пояс на компьютере пользователя настроены корректно, так как расчёт истекающих дедлайнов (≤ 24 ч), просрочек и показателя «серии» (streak) опирается на локальное системное время ОС.
* **Допущение 3:** Пользователь обладает правами записи в пользовательскую директорию данных приложения (например, `%APPDATA%` в Windows или `~/.local/share` в Linux) для создания и обновления файла БД SQLite.
* **Зависимость 1:** Сборка и запуск приложения зависят от наличия компилятора с поддержкой C++17 (GCC, Clang или MSVC), системы сборки CMake и библиотек Qt 6 (`Qt6::Core`, `Qt6::Gui`, `Qt6::Widgets`, `Qt6::Sql`).
* **Риск влияния:** В случае некорректного системного времени на ПК пользователя уведомления об истекающем дедлайне и подсчёт streak могут сместиться; снижается за счёт использования стандартных типов `QDateTime` с учётом локальной временной зоны.

### 3.2 Функциональные требования {#32-functional}

- **ID:** REQ-FUNC-001
- **Title:** Создание новой задачи
- **Statement:** Система должна позволять пользователю создавать новую задачу с обязательным непустым названием (от 1 до 200 символов), необязательным текстовым описанием (до 2000 символов) и необязательным дедлайном (дата и время).
- **Rationale:** Базовая функциональность планировщика задач (BR-1, BR-2).
- **Acceptance Criteria:** После ввода названия и подтверждения создания задача сохраняется в БД SQLite, немедленно отображается в списке задач главного окна со статусом «Не выполнена», а счётчик активных задач увеличивается на 1. Попытка сохранить задачу с пустым названием или состоящим только из пробелов отклоняется с подсказкой пользователю.
- **Verification Method:** Test

- **ID:** REQ-FUNC-002
- **Title:** Редактирование существующей задачи
- **Statement:** Система должна позволять пользователю изменять любые атрибуты ранее созданной задачи (название, описание, дедлайн, категорию, приоритет, правила повторения и список подзадач).
- **Rationale:** Необходимость актуализации параметров задачи при изменении планов пользователя (BR-1).
- **Acceptance Criteria:** При открытии диалога редактирования все поля предзаполнены текущими значениями задачи. После изменения полей и нажатия «Сохранить» обновлённые данные сохраняются в БД и перерисовываются в списке без дублирования записи.
- **Verification Method:** Test

- **ID:** REQ-FUNC-003
- **Title:** Удаление задачи
- **Statement:** Система должна позволять пользователю удалить любую существующую задачу вместе со всеми связанными с ней подзадачами.
- **Rationale:** Удаление ошибочно созданных или потерявших актуальность задач (BR-1).
- **Acceptance Criteria:** При выборе действия удаления и подтверждении операции запись задачи и все её дочерние подзадачи удаляются из БД SQLite и исчезают из интерфейса.

- **Title:** Отметка выполнения и снятие отметки выполнения задачи
- **Statement:** Система должна позволять пользователю переключать статус задачи между состояниями «Активна» и «Выполнена» с фиксацией точного времени завершения (`completed_at`).
- **Rationale:** Отслеживание прогресса выполнения дел и обновление статистики (BR-1, BR-8).
- **Acceptance Criteria:** При установке флажка выполнения статус задачи меняется на «Выполнена», записывается текущая метка времени завершения, обновляется счётчик выполненных задач за день/неделю. При снятии флажка задача возвращается в статус «Активна».
- **Verification Method:** Test

- **ID:** REQ-FUNC-005
- **Title:** Управление приоритетом задачи
- **Statement:** Система должна позволять назначать каждой задаче один из трёх уровней приоритета: «Высокий», «Средний» (значение по умолчанию) или «Низкий», и отображать соответствующий цветовой индикатор в карточке задачи.
- **Rationale:** Визуальное разделение задач по степени важности (BR-3, BG-2).
- **Acceptance Criteria:** В карточке задачи отображается цветовой маркер: красный для высокого приоритета, жёлтый/оранжевый для среднего, зелёный/серый для низкого; изменение приоритета мгновенно обновляет цвет маркера.
- **Verification Method:** Demonstration

- **ID:** REQ-FUNC-006
- **Title:** Создание и переименование категорий задач
- **Statement:** Система должна позволять пользователю создавать пользовательские категории с уникальным названием (от 1 до 50 символов) и выбором цвета метки, а также переименовывать и изменять цвет существующих категорий.
- **Rationale:** Логическая группировка личных, учебных и рабочих задач (BR-4).
- **Acceptance Criteria:** Созданная категория появляется в боковой панели с выбранным цветом и становится доступной в выпадающем списке при создании/редактировании задачи. Попытка создать категорию с уже существующим именем блокируется с информационным сообщением.
- **Verification Method:** Test

- **ID:** REQ-FUNC-007
- **Title:** Удаление категории задач
- **Statement:** Система должна позволять пользователю удалить пользовательскую категорию, переводя все ранее привязанные к ней задачи в состояние «Без категории» без удаления самих задач.
- **Rationale:** Предотвращение случайной потери задач при реорганизации структуры категорий (BR-4).
- **Acceptance Criteria:** После подтверждения удаления категории она исчезает из боковой панели, а у всех задач, принадлежавших этой категории, поле категории сбрасывается в значение по умолчанию («Без категории»), при этом сами задачи остаются в общем списке.
- **Verification Method:** Test

- **ID:** REQ-FUNC-008
- **Title:** Управление подзадачами первого уровня
- **Statement:** Система должна позволять добавлять к любой задаче произвольное количество подзадач первого уровня вложенности, редактировать их названия, удалять их и отмечать каждую подзадачу как выполненную или невыполненную.
- **Rationale:** Декомпозиция сложных задач на последовательные шаги (BR-5).
- **Acceptance Criteria:** Пользователь может добавить от 0 до $N$ подзадач к задаче; состояние каждой подзадачи сохраняется независимо в БД. Вложение подзадачи внутрь другой подзадачи не допускается.
- **Verification Method:** Test

- **ID:** REQ-FUNC-009
- **Title:** Автоматический расчёт прогресса родительской задачи по подзадачам
- **Statement:** Система должна автоматически вычислять и отображать прогресс выполнения родительской задачи как отношение количества выполненных подзадач к общему числу подзадач ($k / N$ и процент выполнения).
- **Rationale:** Наглядная оценка степени готовности составной задачи (BR-5).
- **Acceptance Criteria:** При наличии 3 подзадач и отметке 2 из них как выполненных карточка родительской задачи отображает индикатор `2/3 подзадачи` (67 %). При изменении статуса любой подзадачи индикатор пересчитывается мгновенно.
- **Verification Method:** Test

- **ID:** REQ-FUNC-010
- **Title:** Настройка правил повторения задачи
- **Statement:** Система должна позволять задавать для задачи правило повторения из четырёх режимов: «Ежедневно», «Еженедельно» (с выбором одного или нескольких дней недели: Пн–Вс), «Ежемесячно» (по указанному числу месяца от 1 до 31) и «Произвольный интервал» (через заданное целое число дней $D \ge 1$).
- **Rationale:** Автоматизация регулярных рутинных дел (BR-6, BG-3).
- **Acceptance Criteria:** Выбранное правило повторения сохраняется в параметрах задачи и отображается в её карточке текстовой меткой (например, `каждую неделю, пн` или `ежедневно`). Для ежемесячного повтора по 31-му числу в месяцах с меньшим числом дней дата переносится на последний календарный день этого месяца.
- **Verification Method:** Test

- **ID:** REQ-FUNC-011
- **Title:** Автоматическое создание следующего экземпляра повторяющейся задачи
- **Statement:** При переводе повторяющейся задачи в статус «Выполнена» система должна автоматически создавать новый активный экземпляр этой задачи со следующим расчётным дедлайном согласно её правилу повторения, копируя название, описание, категорию, приоритет и список подзадач (в невыполненном состоянии).
- **Rationale:** Исключение необходимости вручную пересоздавать регулярные задачи после их выполнения (BR-6, BG-3).
- **Acceptance Criteria:** При отметке выполнения еженедельной задачи (по понедельникам) текущая задача остаётся в истории выполненных, а в списке активных задач создаётся новая задача с дедлайном на следующий понедельник и сброшенными статусами всех подзадач.
- **Verification Method:** Test

- **ID:** REQ-FUNC-012
- **Title:** Визуальное выделение истекающих и просроченных дедлайнов
- **Statement:** Система должна автоматически определять задачи с истекающим сроком (до дедлайна осталось $\le 24$ часов) и просроченные задачи (текущее время превысило дедлайн при статусе «Активна») и выделять их цветом и меткой статуса.
- **Rationale:** Снижение риска пропуска дедлайнов (BR-7, BG-2, критерий успеха №3).
- **Acceptance Criteria:** Активная задача, до дедлайна которой осталось менее 24 часов, выделяется предупреждающим янтарным/оранжевым акцентом; активная задача с прошедшим дедлайном выделяется красным акцентом и учитывается в счётчике «Просрочено» в строке состояния. Выполненные задачи не помечаются как просроченные.
- **Verification Method:** Test

- **ID:** REQ-FUNC-013
- **Title:** Подсчёт статистики выполненных задач
- **Statement:** Система должна подсчитывать и отображать количество задач, переведённых в статус «Выполнена» за текущие календарные сутки и за текущую календарную неделю.
- **Rationale:** Информирование пользователя о его текущей продуктивности (BR-8).
- **Acceptance Criteria:** В боковой панели и строке состояния корректно отображается актуальное число выполненных сегодня задач (например, `Сегодня выполнено: 5`); значение обновляется сразу после отметки или снятия отметки выполнения задачи.
- **Verification Method:** Test

- **ID:** REQ-FUNC-014
- **Title:** Расчёт и отображение показателя «серии» (Streak)
- **Statement:** Система должна вычислять и отображать количество последовательных календарных дней, в течение которых у пользователя не было ни одной задачи с истёкшим невыполненным дедлайном («серия» / streak).
- **Rationale:** Геймификация и повышение дисциплины соблюдения сроков (BR-8, BG-3).
- **Acceptance Criteria:** В блоке «Стрик» боковой панели отображается число дней серии (например, `7 дней подряд без пропусков`). Если по завершении календарных суток остаётся хотя бы одна активная задача с дедлайном в этих сутках, серия сбрасывается в `0`.

- **ID:** REQ-FUNC-015
- **Title:** Фильтрация списка задач
- **Statement:** Система должна обеспечивать фильтрацию отображаемого списка задач одновременно или раздельно по выбранной категории, уровню приоритета, временному диапазону срока («Все», «Сегодня», «На неделю», «Просроченные») и статусу выполнения («Активные», «Выполненные», «Все»).
- **Rationale:** Быстрый поиск нужных дел при большом объёме списка (BR-10).
- **Acceptance Criteria:** При выборе категории в боковой панели или установке фильтра в верхней панели список мгновенно обновляется, оставляя только задачи, удовлетворяющие всем активным условиям фильтрации.
- **Verification Method:** Test

- **ID:** REQ-FUNC-016
- **Title:** Сортировка списка задач
- **Statement:** Система должна обеспечивать сортировку отфильтрованного списка задач по одному из критериев: по сроку выполнения (сначала ближайшие/просроченные), по приоритету (от высокого к низкому), по дате создания или по статусу выполнения.
- **Rationale:** Упорядочивание задач в соответствии с текущей стратегией планирования пользователя (BR-10).
- **Acceptance Criteria:** При смене режима сортировки в выпадающем списке «Сортировка» порядок карточек в рабочей области перестраивается в соответствии с выбранным критерием; задачи без дедлайна при сортировке по сроку располагаются в конце списка.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

- **ID:** REQ-PERF-001
- **Title:** Время отклика пользовательского интерфейса
- **Statement:** Время реакции интерфейса на любое локальное действие пользователя (добавление, редактирование, удаление задачи, переключение фильтра или сортировки) не должно превышать $200\text{ мс}$ при объёме базы данных до $5\,000$ задач и $20\,000$ подзадач.

- **Acceptance Criteria:** При нагрузочном тестировании на тестовой БД из $5\,000$ записей замер времени выполнения операций CRUD и фильтрации составляет $\le 200\text{ мс}$ в 99 % случаев.

- **Acceptance Criteria:** На целевой конфигурации (Windows 10/11, Ubuntu 22.04) время от запуска исполняемого файла до готовности UI составляет $\le 1{,}5\text{ с}$, потребление ОЗУ $\le 150\text{ МБ}$.
- **Verification Method:** Test

#### 3.3.2 Безопасность {#332-security}

- **ID:** REQ-SEC-001
- **Title:** Защита от SQL-инъекций при работе с локальной БД
- **Statement:** Все запросы к локальной базе данных SQLite должны выполняться исключительно с использованием параметризованных подготовленных выражений (`QSqlQuery::prepare` / `bindValue`) без конкатенации пользовательского ввода в строку SQL-запроса.
- **Rationale:** Обеспечение целостности локальной базы данных при вводе произвольных спецсимволов и кавычек в названиях и описаниях задач.
- **Acceptance Criteria:** Ввод SQL-конструкций (например, `'; DROP TABLE tasks; --`) в поля названия задачи, описания или категории сохраняется как обычный текст и не нарушает структуру БД.
- **Verification Method:** Test / Inspection

- **ID:** REQ-SEC-002
- **Title:** Конфиденциальность и локальность пользовательских данных
- **Statement:** Система не должна передавать пользовательские задачи, статистику или телеметрию по сети Интернет; все данные должны храниться только в локальном файле базы данных в директории текущего пользователя ОС.
- **Rationale:** Соблюдение требований приватности и концепции offline-first (BR-9, CON-4).
- **Acceptance Criteria:** Мониторинг сетевой активности процесса приложения в течение всего сеанса работы фиксирует 0 исходящих и входящих сетевых соединений.
- **Verification Method:** Test

#### 3.3.3 Надёжность {#333-reliability}

- **ID:** REQ-REL-001
- **Title:** Атомарность сохранения данных и устойчивость к аварийному завершению
- **Statement:** Все операции записи в базу данных SQLite должны выполняться в режиме журналирования `WAL` (Write-Ahead Logging) с использованием транзакций, гарантируя отсутствие повреждения файла БД при внезапном закрытии приложения или отключении питания.
- **Rationale:** Предотвращение потери пользовательских списков дел при сбоях ОС (BR-9).
- **Acceptance Criteria:** После принудительного завершения процесса приложения (`SIGKILL` / «Снять задачу») во время работы база данных `taskflow.db` успешно открывается при следующем запуске, проходит проверку `PRAGMA integrity_check;` со статусом `ok` и сохраняет все ранее подтверждённые задачи.
- **Verification Method:** Test

#### 3.3.4 Доступность {#334-availability}

- **ID:** REQ-AVAIL-001
- **Title:** Непрерывная доступность в автономном режиме
- **Statement:** Приложение должно обеспечивать 100 % функциональности MVP независимо от наличия или отсутствия подключения к сети Интернет, состояния внешних DNS-серверов или облачных сервисов.
- **Rationale:** Выполнение ключевого требования заказчика о работе при нестабильном интернете (BR-9, BG-1).
- **Acceptance Criteria:** При полностью отключённых сетевых интерфейсах («Режим полёта») все функции приложения запускаются и работают без ошибок и задержек.
- **Verification Method:** Demonstration

#### 3.3.5 Наблюдаемость {#335-observability}

- **ID:** REQ-OBS-001
- **Title:** Локальное журналирование ошибок работы с базой данных
- **Statement:** Система должна записывать диагностические сообщения об ошибках открытия, миграции или выполнения транзакций SQLite в локальный файл журнала `taskflow.log` в директории данных приложения с ротацией при достижении размера $5\text{ МБ}$.
- **Rationale:** Упрощение диагностики проблем при эксплуатации на компьютерах пользователей без отправки телеметрии вовне.
- **Acceptance Criteria:** При искусственной блокировке файла БД на запись приложение выводит пользователю понятное сообщение об ошибке и фиксирует код ошибки SQLite с временной меткой в `taskflow.log`.
- **Verification Method:** Test

### 3.4 Соответствие стандартам {#34-compliance}

- **ID:** REQ-COMP-001
- **Title:** Соответствие стандартам оформления и локализации
- **Statement:** Форматирование дат и времени в пользовательском интерфейсе должно соответствовать региональному стандарту `ДД.ММ.ГГГГ ЧЧ:ММ` (ГОСТ / локаль `ru_RU`), а исходный код и документация репозитория должны соответствовать кодировке UTF-8.
- **Rationale:** Единообразие отображения временных меток для русскоязычной аудитории и корректная кириллическая кодировка на Windows и Linux.
- **Acceptance Criteria:** Все сроки выполнения в карточках задач и диалогах отображаются в 24-часовом формате (`18:00`, `11.11.2026 18:00`); все файлы исходного кода и Markdown-документации сохранены в UTF-8 без ошибок отображения кириллицы.
- **Verification Method:** Inspection

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.4 Сопровождаемость {#354-maintainability}

- **ID:** REQ-MAINT-001
- **Title:** Модульная архитектура с разделением слоёв (UI / Бизнес-логика / Данные)
- **Statement:** Архитектура приложения должна разделять представление (Qt Widgets), бизнес-логику (модели задач, движок повторяющихся задач, расчёт streak) и слой хранения данных (SQLite DAO), чтобы изменение UI или правил повторения не требовало переписывания SQL-запросов.
- **Rationale:** Облегчение дальнейшего развития проекта (добавление экспорта в CSV/ICS и календаря в релизе 0.2).
- **Acceptance Criteria:** Классы бизнес-логики (например, `RecurrenceEngine`, `StreakCalculator`) не содержат прямых вызовов виджетов `QWidget` и покрываются модульными тестами независимо от графического интерфейса.
- **Verification Method:** Inspection

#### 3.5.5 Повторное использование {#355-reusability}

- **Rationale:** Подготовка кодовой базы к расширению линейки клиентов в последующих релизах (раздел 2.2 Vision and Scope).
- **Acceptance Criteria:** Заголовочные и исходные файлы модулей `RecurrenceEngine` и `StreakCalculator` компилируются при линковке только с `Qt6::Core` без подключения `Qt6::Widgets` и `Qt6::Sql`.
- **Verification Method:** Analysis / Inspection

#### 3.5.6 Переносимость {#356-portability}

- **ID:** REQ-PORT-001
- **Title:** Кроссплатформенная совместимость между Windows и Linux
- **Statement:** Исходный код приложения не должен использовать платформенно-зависимые системные вызовы WinAPI или POSIX напрямую; работа с путями файловой системы, стандартными директориями приложения (`QStandardPaths`) и временем должна осуществляться средствами стандартной библиотеки C++17 и `Qt6::Core`.
- **Rationale:** Гарантированная работоспособность на ОС Windows 10/11 и Ubuntu Linux без ветвления кодовой базы (CON-5).
- **Acceptance Criteria:** Единая кодовая база без директивы `#ifdef _WIN32` в бизнес-логике успешно компилируется и проходит одинаковый набор функциональных тестов на Windows 10/11 и Ubuntu 22.04.
- **Verification Method:** Test

### Приложение А. Формализация ключевых требований на языке SysML v2

```sysml
package TaskFlowRequirements {
    requirement def TaskPrioritization {
        doc /* Пользователь должен иметь возможность назначать задаче один из уровней
               приоритета: Высокий, Средний, Низкий (BR-3, REQ-FUNC-005). */
    }
    requirement def RecurringTasks {
        doc /* Система должна поддерживать создание повторяющихся задач с заданным
               интервалом: ежедневно, еженедельно, ежемесячно или произвольный интервал
               в днях, с автосозданием следующего экземпляра после выполнения (BR-6, REQ-FUNC-010, REQ-FUNC-011). */
    }
    requirement def Subtasks {
        doc /* Задача должна поддерживать произвольное количество подзадач первого уровня с
               индивидуальным статусом выполнения и агрегированным прогрессом (BR-5, REQ-FUNC-008, REQ-FUNC-009). */
    }
    requirement def OfflineStorage {
        doc /* Все данные приложения должны храниться локально в БД SQLite и оставаться
               доступными без подключения к сети Интернет (BR-9, REQ-INT-003, REQ-AVAIL-001). */
    }
}
```
