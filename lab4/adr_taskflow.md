## ADR-001: Использование локальной встраиваемой СУБД SQLite 3 в режиме WAL для хранения данных

* **status:** accepted
* **date:** 2026-11-27
* **decision-makers:** Грицкевич Кирилл Дмитриевич (Системный архитектор / Исполнитель)
* **consulted:** Напарник (Заказчик по ролевой игре ЛР №4), Внук О.М. (Преподаватель ЖЦРПО)
* **informed:** Junior-разработчик (подключаемый исполнитель)

### Контекст и постановка задачи

Настольному приложению **TaskFlow** требуется надёжно хранить задачи, одноуровневые подзадачи, пользовательские категории и метки времени выполнения локально на рабочей станции пользователя без подключения к сети Интернет (`REQ-INT-003`, `REQ-AVAIL-001`). При этом необходимо обеспечить время отклика интерфейса при фильтрации и поиске не более $200\text{ мс}$ на объёме до $5\,000$ задач (`REQ-PERF-001`) и гарантировать целостность файла данных при аварийном завершении работы (`REQ-REL-001`). Какой механизм постоянного хранения данных выбрать для реализации слоя `TaskFlowData` (`DV-006`)?

### Драйверы решения

* **Полная автономность (Offline-first):** система должна работать без установки внешнего сервера СУБД и без доступа в Интернет (`REQ-AVAIL-001`, `REQ-SEC-002`).
* **Высокая производительность:** время выполнения операций чтения, фильтрации и записи не должно превышать $200\text{ мс}$ на $5\,000$ задач (`REQ-PERF-001`).
* **Целостность и отказоустойчивость:** отсутствие потери данных при внезапном закрытии процесса и поддержка ссылочной целостности между задачами, подзадачами и категориями (`REQ-REL-001`, `REQ-FUNC-003`, `REQ-FUNC-007`).
* **Нулевая стоимость и кроссплатформенность:** бесплатная лицензия и работа на Windows 10/11 и Ubuntu Linux (`REQ-COST-001`, `REQ-PORT-001`).

### Рассмотренные варианты

* Встраиваемая реляционная СУБД SQLite 3 в режиме WAL (через `Qt6::Sql`)
* Текстовые файлы формата JSON / XML с сериализацией в памяти
* Локальная клиент-серверная СУБД PostgreSQL

### Итог решения

Выбранный вариант: **«Встраиваемая реляционная СУБД SQLite 3 в режиме WAL (через `Qt6::Sql`)»**, потому что это единственный вариант, обеспечивающий транзакционную целостность (ACID), каскадное управление связями через внешние ключи (`ON DELETE CASCADE / SET NULL`) и индексированный поиск за $< 5\text{ мс}$ без необходимости развёртывания отдельного серверного процесса у конечного пользователя.

### Последствия

* **Хорошо, потому что:** база данных хранится в одном переносимом файле `taskflow.db`, поддерживает реляционные ограничения целостности на уровне схемы и защищена журналом `WAL` от повреждения при сбоях питания.
* **Хорошо, потому что:** нативная интеграция с модулем `Qt6::Sql` (`QSQLITE`) и параметризованными запросами `QSqlQuery::bindValue` закрывает риск SQL-инъекций (`REQ-SEC-001`).
* **Плохо, потому что:** требуется проектирование реляционной схемы таблиц, индексов и механизма начальной миграции при первом запуске приложения.

### Подтверждение

Соблюдение решения проверяется:
1. Инспекцией SQL-схемы (`DV-006`) на наличие `PRAGMA foreign_keys = ON;` и `PRAGMA journal_mode = WAL;`.
2. Модульными тестами репозиториев (`tests/test_sqlite_dao.cpp`, `tests/test_security_sql.cpp`) и тестом восстановления после принудительного завершения процесса (`tests/test_wal_recovery.md` — проверка `PRAGMA integrity_check;`).

### Плюсы и минусы вариантов

#### Встраиваемая реляционная СУБД SQLite 3 в режиме WAL (через `Qt6::Sql`)

Хранение сущностей в нормализованных таблицах `categories`, `tasks`, `subtasks` в локальном файле `taskflow.db`.

* **Хорошо, потому что** не требует установки и администрирования сервера БД на ПК пользователя (`REQ-INST-001`).
* **Хорошо, потому что** поддерживает внешние ключи (`ON DELETE CASCADE` для подзадач и `ON DELETE SET NULL` при удалении категории) и быстрые B-Tree индексы.
* **Хорошо, потому что** распространяется в общественном достоянии (Public Domain) и встроена в стандартную поставку Qt 6 (`REQ-COST-001`).
* **Плохо, потому что** требует написания слоя DAO и маппинга строк `QSqlQuery` в объекты C++ (`Task`, `Subtask`, `Category`).

#### Текстовые файлы формата JSON / XML с сериализацией в памяти

Полная выгрузка и перезапись файла `tasks.json` при каждом изменении статуса или атрибутов задачи.

* **Хорошо, потому что** файл легко читается человеком в текстовом редакторе и не требует написания SQL-запросов.
* **Плохо, потому что** при аварийном завершении программы в момент записи файл с высокой вероятностью будет повреждён (нарушение `REQ-REL-001`).
* **Плохо, потому что** полная сериализация $5\,000$ задач с подзадачами при каждом клике увеличивает задержку и риск потери данных.

#### Локальная клиент-серверная СУБД PostgreSQL

Установка отдельного сервиса PostgreSQL на компьютер пользователя.

* **Хорошо, потому что** предоставляет максимальную масштабируемость и богатые возможности SQL.
* **Плохо, потому что** критически усложняет установку приложения для обычного пользователя (нарушение `REQ-INST-001`) и избыточно расходует оперативную память сверх лимита $150\text{ МБ}$ (`REQ-PERF-002`).

### Дополнительная информация

Решение зафиксировано в представлении `DV-006` документа SDD (`sdd/sdd-taskflow.md`). Пересмотр решения потребуется только в релизе 0.2+ при появлении требований многопользовательской облачной синхронизации.

## ADR-002: Трёхслойная архитектура с изоляцией ядра `TaskFlowCore` от Qt Widgets и SQL

* **status:** accepted
* **date:** 2026-11-27
* **decision-makers:** Грицкевич Кирилл Дмитриевич (Системный архитектор / Исполнитель)
* **consulted:** Внук О.М. (Преподаватель ЖЦРПО)
* **informed:** Напарник (Заказчик), Junior-разработчик

### Контекст и постановка задачи

В проекте **TaskFlow** необходимо реализовать нетривиальную бизнес-логику расчёта повторяющихся задач (`RecurrenceEngine`) и непрерывной серии выполнения (`StreakCalculator`), обеспечить её переиспользование в будущих версиях (`REQ-REUSE-001`), упростить сопровождение (`REQ-MAINT-001`) и распараллелить разработку между ведущим разработчиком и подключаемым junior-разработчиком. Как организовать модульную структуру и зависимости проекта?

### Драйверы решения

* **Переиспользуемость ядра:** бизнес-логика должна компилироваться без зависимости от графического интерфейса и конкретной СУБД (`REQ-REUSE-001`).
* **Тестируемость:** ключевые алгоритмы (повторения, граничные даты месяца, streak) должны проверяться автоматическими модульными тестами без запуска GUI.
* **Сопровождаемость и параллельная работа:** чёткие границы модулей для независимой работы двух разработчиков (`REQ-MAINT-001`).

### Рассмотренные варианты

* Трёхслойная архитектура (`UI` $\rightarrow$ `Core` $\leftarrow$ `Data`) с инверсией зависимостей через интерфейсы репозиториев
* Двухслойная архитектура (UI-виджеты напрямую вызывают классы работы с SQLite)
* Монолитная архитектура с размещением логики и SQL-запросов в классах окон и диалогов Qt

### Итог решения

Выбранный вариант: **«Трёхслойная архитектура (`UI` $\rightarrow$ `Core` $\leftarrow$ `Data`) с инверсией зависимостей через интерфейсы репозиториев»**, потому что она полностью изолирует библиотеку `TaskFlowCore` (зависящую только от `C++17` и `Qt6::Core`), позволяет тестировать бизнес-логику с помощью mock-репозиториев в памяти и даёт возможность безопасно делегировать задачи слоя UI и фильтрации junior-разработчику.

### Последствия

* **Хорошо, потому что:** модули `RecurrenceEngine` и `StreakCalculator` можно повторно использовать в будущем мобильном или консольном клиенте без изменений (`REQ-REUSE-001`).
* **Хорошо, потому что:** исключаются конфликты слияния в Git между логикой БД/повторений и версткой виджетов.
* **Плохо, потому что:** увеличивается количество абстрактных интерфейсов (`ITaskRepository`, `ICategoryRepository`) и шаблонного кода передачи данных между слоями.

### Подтверждение

Проверка выполняется через конфигурацию сборки `CMakeLists.txt` (`DV-005`): цель `TaskFlowCore` линкуется строго с `Qt6::Core` (без `Qt6::Widgets` и `Qt6::Sql`), что гарантирует невозможность случайного импорта GUI- или SQL-заголовков на этапе компиляции.

### Плюсы и минусы вариантов

#### Трёхслойная архитектура (`UI` $\rightarrow$ `Core` $\leftarrow$ `Data`) с инверсией зависимостей

Разделение проекта на три статические библиотеки CMake: `TaskFlowCore`, `TaskFlowData` и исполняемый модуль `TaskFlowApp`.

* **Хорошо, потому что** полностью удовлетворяет требованиям `REQ-MAINT-001` и `REQ-REUSE-001`.
* **Хорошо, потому что** обеспечивает высокую скорость прогона модульных тестов в памяти без обращения к диску.
* **Плохо, потому что** требует предварительного проектирования контрактов C++ (`DV-007`) до начала параллельной разработки.

#### Двухслойная архитектура (UI напрямую вызывает слой SQLite)

Окна и диалоги Qt напрямую используют `SqliteTaskRepository` и содержат логику расчёта повторений и streak.

* **Хорошо, потому что** сокращает число классов и прослоек на старте проекта.
* **Плохо, потому что** нарушает требование `REQ-REUSE-001` о независимости модулей расчёта повторений и статистики от `Qt6::Widgets` и `Qt6::Sql`.
* **Плохо, потому что** усложняет автоматическое тестирование граничных случаев календаря.

#### Монолитная архитектура в классах виджетов

Размещение SQL-запросов и бизнес-логики внутри слотов `MainWindow` и `TaskDialog`.

* **Хорошо, потому что** позволяет максимально быстро написать первый прототип.
* **Плохо, потому что** приводит к высокой связанности кода, дублированию SQL-запросов и высокому риску регрессий при добавлении новых требований Заказчика.

### Дополнительная информация

Архитектурное решение отражено в представлениях `DV-002`, `DV-004`, `DV-005` и `DV-007` документа SDD (`sdd/sdd-taskflow.md`).

## ADR-003: Привлечение Junior-разработчика для сохранения дедлайна при добавлении нового требования Заказчиком

* **status:** accepted
* **date:** 2026-11-27
* **decision-makers:** Грицкевич Кирилл Дмитриевич (Исполнитель / Архитектор), Напарник (Заказчик по ролевой игре ЛР №4)
* **consulted:** Внук О.М. (Преподаватель ЖЦРПО)
* **informed:** Junior-разработчик

### Контекст и постановка задачи

В ходе второго раунда обсуждения плана реализации по Лабораторной работе №4 Заказчик потребовал включить в первый релиз важный функционал — подсистему статистики выполненных задач и расчёта непрерывной «серии» (`F-09`: `REQ-FUNC-013`, `REQ-FUNC-014`, трудоёмкость 10 ч), но категорически отказался сдвигать дедлайн выпуска ПО (2 недели) и существенно увеличивать бюджет проекта. Как обеспечить выполнение всего согласованного объёма MVP в исходный срок без критического превышения стоимости?

### Драйверы решения

* **Жёсткий дедлайн выпуска:** срок поставки MVP фиксирован и составляет 2 недели (2 итерации по 5 рабочих дней) (`REQ-DEAD-001`).
* **Ограничение бюджета:** Заказчик не согласен на кратное удорожание проекта за счёт привлечения дорогостоящих специалистов.
* **Сохранение качества:** сложная алгоритмическая часть (SQLite WAL, движок повторяющихся задач) должна оставаться под контролем ведущего разработчика (`REQ-REL-001`, `REQ-FUNC-010`).

### Рассмотренные варианты

* Привлечь одного Junior-разработчика на изолированные модули под ревью ведущего разработчика
* Сдвинуть дедлайн релиза на 1 неделю вперёд при работе одного ведущего разработчика
* Нанять второго Senior-разработчика для ускорения разработки

### Итог решения

Выбранный вариант: **«Привлечь одного Junior-разработчика на изолированные модули под ревью ведущего разработчика»**, потому что трёхслойная архитектура (`ADR-002`) позволяет выделить автономные задачи с низким риском (`F-03` приоритеты, `F-04` категории, `F-06` визуальное выделение дедлайнов, `F-08` фильтрация и сортировка, `F-09` статистика и streak), уложиться в исходный дедлайн 2 недели и удержать рост стоимости в минимальных пределах ($1288\text{ у.е.}$ вместо $1720\text{ у.е.}$).

### Последствия

* **Хорошо, потому что:** сохраняется исходная дата релиза MVP без урезания функциональных требований `BR-1…BR-10`.
* **Хорошо, потому что:** стоимость разработки увеличивается незначительно за счёт более низкой ставки junior-разработчика ($8\text{ у.е./ч}$ против $20\text{ у.е./ч}$ у ведущего разработчика).
* **Плохо, потому что:** ведущему разработчику требуется выделить 6 часов (4 ч в 1-й итерации и 2 ч во 2-й итерации) на постановку задач, проектирование интерфейсов и обязательное код-ревью Pull Request'ов junior-разработчика.

### Подтверждение

Соблюдение решения подтверждается:
1. Утверждённым итерационным планом (Приложение А.2 в `sdd/sdd-taskflow.md`).
2. Обязательным прохождением Pull Request и модульных тестов (`tests/test_streak.cpp`, `tests/test_filter_sort.cpp`) перед слиянием веток junior-разработчика в `main` (`REQ-CM-001`).

### Плюсы и минусы вариантов

#### Привлечь одного Junior-разработчика на изолированные модули под ревью ведущего разработчика

Делегирование задач UI, фильтрации и изолированного калькулятора статистики (`36 ч` работы Junior + `6 ч` ревью Lead).

* **Хорошо, потому что** позволяет выполнить весь увеличенный объём работ строго в исходный дедлайн (2 недели).
* **Хорошо, потому что** обеспечивает минимальную итоговую стоимость проекта ($1288\text{ у.е.}$) в рамках ограничений Заказчика.
* **Плохо, потому что** требует затрат времени ведущего разработчика на онбординг и проверку кода.

#### Сдвинуть дедлайн релиза на 1 неделю вперёд при работе одного ведущего разработчика

Выполнение всех $80\text{ ч}$ разработки силами одного Lead-разработчика ($80\text{ ч} \times 20\text{ у.е./ч} = 1600\text{ у.е.}$) за 3 недели.

* **Хорошо, потому что** не требует координации команды и затрат на код-ревью.
* **Плохо, потому что** нарушает жёсткое требование Заказчика по дате выпуска ПО и обходится дороже, чем привлечение junior-разработчика.

#### Нанять второго Senior-разработчика

Привлечение второго специалиста со ставкой $20\text{ у.е./ч}$ на $36\text{ ч}$ ($720\text{ у.е.}$).

* **Хорошо, потому что** гарантирует высокий темп и минимальные затраты на ревью.
* **Плохо, потому что** приводит к существенному росту бюджета проекта ($1720\text{ у.е.}$), что отклонено Заказчиком.

### Дополнительная информация

Согласовано в ходе второго раунда ролевой переписки с Заказчиком по Лабораторной работе №4. Детальная разбивка часов по итерациям приведена в Приложении А документа SDD (`sdd/sdd-taskflow.md`).
